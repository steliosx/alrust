## Owner decisions: merges, protection and reference defects (2026-10-01, given in Claude's session)

| # | Question | Decision |
|---|---|---|
| Y1 | Merging the approved pull requests | **Merge.** The owner instructed Claude to merge PR #2 and the approved PRs. Done for PRs #1–#10 (merge commits listed in `docs/STATUS.md`): each was retargeted to `main` only after its base had merged, and its diff was confirmed unchanged against the reviewed diff (patch-id) before a merge pinned to the approved head. PR #2's README conflict with PR #1 was resolved to PR #2's reviewed README byte for byte. Then Codex's chain: PR #14 first conflicted with the merged ADR-0002 text; Codex supplied a reviewed successor (`2811c700`, approved by Claude), named the merge set, and #14, #15, #17, #21, #24–#26 and #28–#36 were merged the same way (#17 bringing #16 and its HF9 correction together). `main` is at `51721391`, tree as simulated in advance. Codex closed its superseded PRs (#11, #12, #13, #16, #18–#20, #22, #23, #27). Merge authority was exercised by Claude on the owner's explicit instruction, for these PRs only |
| Y2 | Repository protection (`docs/repo-protection-recommendation.md`) | **Approved.** Not applied: GitHub refuses branch protection and rulesets on this private repository without GitHub Pro or making it public (HTTP 403). **Route chosen (2026-10-01): make the repository public later, after the beta has been tested; no paid upgrade.** Until then `main` has no protection and the reference guard is not enforced. Required reviews cannot be satisfied while both agents use the owner's login |
| Y3 | Reference security and behavior defects (the owner items in `docs/STATUS.md`) | **alrust fixes them; it does not reproduce them.** This covers the four string-formatted SQL constructions; AN1 (`ALLOW_READONLY` dispatching without a scope check); the users role-ceiling bypass and the related user-creation defects; G-SEC-1, P-SEC-1 and C-SEC-1 with GR-R1 and G-DEF-1; M-SEC-1 (`/management/properties` secrets); WUI-SEC-1 and WP-SEC-1; W-SEC-1 (credentials in webhook logs) and W-DL-1 (multi-alert webhook data loss); the API-key expiry, scope and secret-exposure items; C21–C23; the `q=` search dropping operands; and the App Engine cron branch. The exact behavior of each fix is specified per item in `spec/security-fixes.md`, under Codex review, and every deliberate divergence from the reference is recorded so that the conformance suite and the differential fuzzer expect it. Specified and approved so far: SF-AN1, SF-CRON, SF-USERS (PR #40) and SF-GROUPS, SF-PERMS, SF-CUSTOMERS (PR #42) |
| Y4 | Checking production exposure (version and settings in production) | **Deferred** by the owner |
| Y5 | Standing merge permission (2026-10-01) | **Claude merges every pull request once the other agent has approved its exact head** (Codex for Claude's pull requests, Claude for Codex's), documentation, specifications, conformance and CI workflow changes alike, with the same checks: retarget only after the base has merged, the diff equal to the reviewed diff (patch-id), mergeability, a merge pinned to the approved head, merge commits only, branches kept. Releases stay with the owner. This supersedes X7's owner merge of the x64 workflow: Claude merges it after Codex approves it. (Wording clarified on 2026-10-01: the owner's instruction was "Claude merges all approved PRs") |
| Y6 | API-key secrets (2026-10-01) | **Show the secret only once**: alrust returns a key's secret only in the response that creates it; every other response omits it, links use the key id, and keys are addressed by id only. Accepted cost: the pinned web UI's key list can no longer show or copy existing keys. **Amended (2026-10-01):** the pinned web UI ignores the creation response, so it would never show a new key's secret; on Claude's corrected question the owner chose to **patch alrust's vendored web UI to show the secret once after creation**, with a copy control. Specified in `spec/security-fixes.md` SF-KEYS |
| Y7 | API-key edit ceiling (2026-10-01) | **Always check:** when a key is edited (`PUT /key/{id}`), its resulting scopes, sent in the request or already stored, must not exceed the caller's scopes, else HTTP 403. A user can no longer change, or extend the expiry of, a key granted above their own permissions; an admin must edit it. The web UI already sends the scopes, so UI behavior is unchanged. Other options offered: check only expiry changes; keep the reference behavior. Specified in `spec/security-fixes.md` SF-KEYS |
| Y8 | Management properties endpoint (2026-10-01) | **Redacted settings:** `GET /management/properties` keeps its `admin:management` scope and returns alrust's effective settings as text, with every secret value replaced by `[REDACTED]` (secret-named settings, credentials and paths in URLs). Process environment variables and request data are not dumped. Other options offered: remove the endpoint; keep the full dump. Specified in `spec/security-fixes.md` SF-MGMT |
| Y9 | Token signing key (2026-10-01) | **Generate a random key:** if `SECRET_KEY` is not set (also when empty or the reference default `changeme`), alrust generates a random key at each start and logs a warning. Accepted cost: every restart logs users out and invalidates e-mail and password-reset links, and several instances need one configured key. Other options offered: refuse to start; start with a warning. Specified in `spec/security-fixes.md` SF-MGMT |
| Y10 | Webhook batches (W-DL-1, 2026-10-01) | **Process every alert:** when one webhook call carries several alerts, each is handled independently, so a blackout, heartbeat, rate limit, rejection or error on one alert never drops the others. The HTTP status is the one the reference would have returned for the first alert not stored, so senders retry as they do today; the body lists each alert's outcome. Other options offered: all or nothing; keep the reference behavior. Specified in `spec/security-fixes.md` |
| Y11 | Web UI rendering (WUI-SEC-1, 2026-10-01) | **Plain text with auto-links:** alrust's vendored web UI shows alert, history, attribute and group-member fields as plain text; http(s) addresses become safe links that open in a new tab, and HTML is shown literally. The Prometheus webhook stores the plain URL in `moreInfo` instead of an HTML link. Accepted cost: formatting that senders put in alert text is not rendered. Other options offered: sanitized HTML; keep raw HTML. Specified in `spec/security-fixes.md` |
| Y12 | Prometheus placeholders (WP-SEC-1, 2026-10-01) | **Plain names only:** in Prometheus labels and annotations, only `{name}` is replaced by that label's value (`{{` and `}}` stay literal braces); widths, format specs, attribute and index access and conversions are left as written; an expansion longer than 64 KiB keeps the original text. Other options offered: no expansion; full Python syntax with caps. Specified in `spec/security-fixes.md` |

# PostgreSQL 19.0 against 18.7 for Alerta: reads the same, writes slightly slower or the same, 21 November 2026

One full run of the `pg19` suite. It runs Alerta 9.1.0 on PostgreSQL 18.7 and on PostgreSQL 19.0,
side by side on one hosted runner, with the same data and the same settings for each version. The
numbers are diagnostic and relative to that runner. They are not a capacity claim, and they are not
a recommendation to upgrade.

## Answer in short

- **Alerta 9.1.0 runs on PostgreSQL 19.0.** All 108 cells are valid, and every data check passed.
- **Reads: the same on both versions.** The twelve read medians lie between -0.1% and +2.1%.
- **Writes: the same or slightly slower on 19.0.** Five of the six duplicate-write medians are
  negative (-0.9% to -5.6%; the sixth is +0.6%). The run has no 18.7-against-18.7 control, so it
  cannot say whether this pattern is more than the runner's noise.
- **One row is outside that range.** Write-dup at 8 clients, arm `alerta-4x4-pgbu-nofwd`: median
  -5.6%. All three of its repetitions are below zero (-7.3%, -5.6%, -0.2%). Its p50 improved
  (10.37 to 9.31 ms) while its p99 worsened (16.51 to 20.90 ms). This run does not say why, and one
  run cannot settle it.
- **Not tested here:** alrust (this suite has no alrust arm), and any PostgreSQL 19 feature on its
  own. Both versions ran with the same settings.

### Arms

The suite runs each arm on both versions. Alerta's code is the same in every arm. `4x4` means 4
gunicorn workers with 4 threads each (one worker process per vCPU).

| Arm | What it is |
|---|---|
| `alerta-4x4-nofwd` | Direct connections to the PostgreSQL server, with the default plugins minus `forwarder`. |
| `alerta-4x4-pgbu-nofwd` | The same, through PgBouncer on its Unix socket with `trust` (one PgBouncer serves both clusters). The suite names this the best-settings arm. |
| `alerta-4x4-safe-nofwd` | The same, with the add-on's `safe` patches: `reuse`, `nolog`, `onecount` and `nosentry`. Each leaves Alerta's own writes as they are. |

alrust is not in this suite. Its PostgreSQL pin is 18.7, and this run does not change it.

### Order

In each repetition the two versions of one arm run one after the other. The arms move by one place
each repetition, and which version runs first changes with the arm and the repetition
(`pair_order()`). The order is written to the record. Each arm's pair runs in this order:

| Repetition | Order (version, arm) |
|---|---|
| 0 | 18.7 `nofwd`, 19 `nofwd`, 19 `pgbu`, 18.7 `pgbu`, 18.7 `safe`, 19 `safe` |
| 1 | 18.7 `pgbu`, 19 `pgbu`, 19 `safe`, 18.7 `safe`, 19 `nofwd`, 18.7 `nofwd` |
| 2 | 18.7 `safe`, 19 `safe`, 18.7 `nofwd`, 19 `nofwd`, 19 `pgbu`, 18.7 `pgbu` |

Version 18.7 ran first for `nofwd` and `safe` in two repetitions, and first for `pgbu` in one.
Both clusters ran for the whole suite, each on its own port. Only one had load at a time. The seed
database, on 18.7, was dumped and restored into each cluster with that cluster's own tools, then
analyzed. Each cell ran on its own copy of the restored database.

## Checks

- 108 of 108 cells valid. None missing, none twice.
- 18 of 18 read checks passed: one for each version, arm and repetition. Each one compared the total,
  the 50 newest ids, every listed alert's fields with the database, the count's groups with SQL, and
  the list and count bodies with the first arm's (`pg18-alerta-4x4-nofwd-r0`), `href` origins aside.
- 36 of 36 write cells saved every counted write. After the warm-up and after the timed run, the
  duplicate alert's `duplicate_count` had grown by exactly the 2xx answers, with one row and the same
  id.
- Every raw sample file matched the numbers of its cell when computed again. No file name was used
  twice.
- The gate's self-test passed: 12 cases, as expected.

## What the run shows

- **Reads and writes differ.** The twelve read medians lie between -0.1% and +2.1%. Five of the six
  write medians are negative. No row shows a large change, and the run has no control pair to judge
  the write pattern.
- **The write row at 8 clients with `pgbu` is the exception.** Its median is -5.6%, and it is the only
  row where all three repetitions are below zero. Its PostgreSQL CPU per request is the same on both
  versions (1.448 and 1.443 ms), so this run gives no CPU reason for the gap. One run is not enough
  to tell whether the gap is real.
- **The noise is in the repetitions, not in the versions.** The summary of this run states: "A change
  of a few percent is inside the noise of one runner." The suite's own description says the same,
  as "a difference of a few percent is inside the noise between repetitions." The per-repetition
  changes run from -7.3% to +8.7%, and the largest are in the `pgbu` arm.
- **Same version, different repetitions.** On 18.7 the widest spread in one row was list at 8 clients
  with `pgbu`: 396.4 to 448.2 requests per second. On 18.7 count at 1 client with `nofwd` stayed
  between 132.1 and 133.2. The run has no control pair of 18.7 against 18.7, so it does not measure
  the false-positive rate of its own comparison.
- **Nothing here says which settings or features of 19.0 caused any change.** The run compares two
  versions with the same settings. It does not turn on any 19.0 feature.

## Limits

- One hosted runner with 4 vCPUs. The servers, both PostgreSQL versions, PgBouncer and the load tool
  share it, over loopback.
- Three repetitions of each arm and version, and the version that ran first changed between them.
- 1000 seeded alerts, which the suite says fit in memory. The read cases are the 50 newest alerts
  and the count. The write case sends one fixed duplicate alert.
- Default server settings, the same for both versions: `scripts/bench/setup.sh` starts both
  clusters with the same initdb options, `listen_addresses=127.0.0.1`, no server Unix socket and
  `max_connections=200` on the command line. No other setting appears there, and no setting was
  tuned for either version.
- Only Alerta 9.1.0, in three arms. alrust is not in this suite.
- No PostgreSQL 19 feature was tested on its own.
- This is not a recommendation to upgrade, and it does not change alrust's PostgreSQL 18.7 pin.
